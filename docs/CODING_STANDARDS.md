# Coding Standards

**The** reference for how code and content are written in this project. Every contributor, human or AI, follows it.
If a situation isn't covered: copy the closest existing pattern in the codebase, then add the rule here in the
same change so the next person doesn't have to guess.

## 1. Folder structure

```
/                               repo root = Unity project root
├─ README.md, CLAUDE.md, AGENTS.md
├─ docs/                        design, architecture, standards, how-tos
├─ Packages/manifest.json
├─ ProjectSettings/
└─ Assets/
   ├─ _Project/                 ALL first-party files live here (underscore sorts it first)
   │  ├─ Scenes/                Main.unity (generated by the editor bootstrapper)
   │  ├─ Resources/Content/     ScriptableObject content, one sub-folder per type
   │  │  ├─ Ship/  Weapons/  Enemies/  Milestones/  Config/
   │  ├─ Scripts/
   │  │  ├─ Runtime/            AstroIdle.Runtime.asmdef
   │  │  │  ├─ Utilities/ Content/ Events/ Persistence/ Progression/
   │  │  │  ├─ Gameplay/{Arena,Combat,Effects,Enemies,Player,Waves,Weapons}/
   │  │  │  ├─ Core/ UI/{Bindings,Tabs}/ Bootstrap/
   │  │  └─ Editor/             AstroIdle.Editor.asmdef (editor-only tools)
   │  └─ Tests/EditMode/        AstroIdle.Tests.EditMode.asmdef
   └─ (third-party packages/assets go in their own top-level folders, never inside _Project)
```

Rules:
- New runtime code goes in the folder for its **layer** (see §2). If no folder fits, discuss and document a new one
  here before creating it.
- One folder = one namespace (§3). Every code folder has a `README.md` (§13).
- Art, audio and prefabs (when they arrive) go in `Assets/_Project/Art/`, `Audio/`, `Prefabs/`, organized by
  feature. Anything loaded by path goes under `Resources/` with the path constant defined in code.

## 2. Layering & dependencies

Dependencies point **one way only** (a layer may use the layers before it):

```
Utilities → Content → Events → Persistence → Progression → Gameplay → Core → UI → Bootstrap
```

- `Progression` has **no MonoBehaviours** and never references `Gameplay` or `UI`.
- `Gameplay` never references `UI`, `Core` or `Bootstrap`. It reports outward via `GameEvents`.
- `UI` reads state and calls service methods (commands). It holds **no game rules**. A rule like "can I afford
  this?" belongs in a service the UI asks.
- `Bootstrap` is the only place that *constructs* services and wires them together (composition root).
- Inside `Gameplay`, sub-namespaces may reference each other.
- Editor and test assemblies may reference anything in Runtime. Runtime must never reference them.

## 3. Namespaces & assemblies

- Namespace = `AstroIdle` + folder path after `Runtime/`. Example: `Scripts/Runtime/Gameplay/Enemies/Enemy.cs` →
  `AstroIdle.Gameplay.Enemies`.
- Editor code: `AstroIdle.Editor`. Tests: `AstroIdle.Tests`.
- Assemblies: `AstroIdle.Runtime` (all runtime), `AstroIdle.Editor` (editor-only), `AstroIdle.Tests.EditMode`.
  Don't add an asmdef without updating this doc and the Scripts README.

## 4. Naming

| Thing | Convention | Example |
|-------|------------|---------|
| Types, methods, properties, events, constants | PascalCase | `WaveDirector`, `TryPurchase`, `MaxHull`, `RefreshInterval` |
| Private fields, locals, parameters | camelCase, **no** `_` or `m_` prefix | `spawnTimer`, `context` |
| Serialized private fields | camelCase with `[SerializeField] private` | `[SerializeField] private float moveSpeed = 3f;` |
| Public DTO fields (save data only) | camelCase public fields | `SaveData.highestWave` |
| Interfaces | `I` + PascalCase | `IEnemyBehaviour`, `IRowBinding` |
| Bool members | Is/Has/Can prefix | `IsActive`, `HasButton`, `CanPurchase` |
| Event-raising methods | `Raise` + event name | `RaiseEnemyKilled` |
| Event handlers | `On` + event name | `OnEnemyKilled` |
| ScriptableObject types | `…Definition` (a content item) or `…Config` (singleton settings) | `EnemyDefinition`, `WaveConfig` |
| MonoBehaviour UI classes | `…View` (`…Root` for the root) | `HudView`, `UIRoot` |
| UI data adapters | `…Binding` | `UpgradeRowBinding` |
| Services (plain C#) | `…Service`, or a noun for a clear role | `UpgradeService`, `CurrencyWallet`, `WeaponInventory` |
| Content asset files | `Type_Name.asset` (PascalCase) | `Weapon_PulseBlaster.asset`, `Enemy_Drone.asset` |
| Milestone asset files | `Milestone_NN_Name.asset` (NN = sort order) | `Milestone_03_ScatterLicense.asset` |
| Content ids (in data) | lower_snake_case, permanent | `pulse_blaster`, `asteroid_shard` |
| Docs | `README.md` per folder, `UPPER_SNAKE.md` in `docs/` | `GAME_DESIGN.md` |

Spelling: use **Behaviour** (Unity's British spelling) for consistency with `MonoBehaviour`.

## 5. Files & formatting

- **One public type per file**, and the file name matches the type (required by Unity for MonoBehaviours and
  ScriptableObjects). Small private nested types are fine.
- 4-space indentation, Allman braces (opening brace on its own line), LF line endings, UTF-8. `.editorconfig`
  enforces most of this.
- `using` directives at the top, `System*` first, then alphabetical. Remove unused ones.
- Member order: constants → static fields → serialized fields → private fields → properties → Unity messages
  (`Awake`, `OnEnable`, `Start`, `Update`, `OnDestroy`) placed with private methods → public methods. Keep public
  API near the top when it helps readability. Be consistent within a file.
- Use `var` when the type is obvious from the right-hand side. Otherwise write the type.
- Prefer early returns over deep nesting.
- Max line length about 140 characters.

## 6. C# patterns

- **Explicit dependencies:** pass collaborators through constructors (plain classes) or an `Initialize(...)`
  method (MonoBehaviours). No service locators, no singletons with `Instance`, no `static` mutable state except
  `GameEvents` and caches that reset in `[RuntimeInitializeOnLoadMethod(SubsystemRegistration)]`.
- **Plain C# by default.** Use `MonoBehaviour` only when you need the Unity lifecycle (`Update`), a `Transform`
  or components. Rules and math go in plain classes or `static` pure functions (which are testable).
- **Encapsulate state:** expose read-only properties. Mutation goes through intention-revealing methods
  (`TrySpend`, `TryPurchase`, `TryUnlock`).
- **`Try…` methods** return `bool` for expected failures (can't afford). Use exceptions only for programmer errors.
- **Strategy over switch-everywhere:** variable behaviour (enemy AI, tabs, rows) is an interface with
  implementations, selected in one factory or registry.
- **Comments:** every public type gets a `<summary>` saying what it is *for*. Comment *why*, not *what*.
  Point to the design doc for balance reasoning instead of duplicating it.
- **No magic numbers** in logic: use a named `const` at the top of the class, or (for anything a designer might
  tune) a field on a Definition/Config asset.
- Use `double` for currency and costs. Use `float` for spatial and combat values.

## 7. Unity patterns

- **The scene stays empty:** only `Main Camera` and `GameBootstrap`. Everything else is created in code by the
  bootstrap or factories. Don't add objects to the scene by hand.
- **No `Find*` calls** (`GameObject.Find`, `FindObjectOfType`, `FindFirstObjectByType`, `GetComponent` on other
  objects for discovery). Get references by injection.
- **Pooling:** anything spawned repeatedly (enemies, projectiles, particles) uses `UnityEngine.Pool.ObjectPool` or
  a fixed ring buffer. Despawn methods must be idempotent (guard with `IsActive`).
- **Re-entrancy:** when an action can trigger a big state change (ship death → clear all enemies), set a flag and
  handle it next frame in the owning system (see `WaveDirector.pendingFail`). Remove yourself before damaging
  others (see `Enemy.CheckPlayerContact`).
- **Time:** gameplay uses `Time.deltaTime` (respects the DEV speed-up). UI timers and autosave use
  `Time.unscaledDeltaTime`.
- **Input:** UI-only for now. Code must compile with both input backends (`#if ENABLE_INPUT_SYSTEM`). Never call
  the legacy `UnityEngine.Input` API directly.
- **UI:** build through `UiFactory`. Colors and font sizes come from `UiTheme` (never inline). Screen regions come
  from `ScreenLayout`.
- **Generated textures/sprites** must be destroyed when replaced (see `Starfield.ReleaseGenerated`).
- **Editor-only code** goes in `Scripts/Editor/` (editor asmdef), never behind `#if UNITY_EDITOR` in runtime
  files unless unavoidable.

## 8. Content & data rules

- Balance numbers and content live in **assets**, not code. Defaults in Definition classes are placeholders for
  newly created assets only.
- ScriptableObject fields: `[SerializeField] private` + public read-only property. Add `[Header]` groups and a
  `[Tooltip]` on anything non-obvious (units, ranges, 0 = special meaning).
- Reference other content by **string id**, validated in `ContentDatabase.Validate()`. Add a validation rule for
  every new cross-reference.
- **Serialized enums are append-only with explicit values.** Never reorder, renumber or delete a member. Mark
  retired members `[Obsolete]` instead.
- **Ids and upgrade track ids are permanent** once shipped (they're in save files).
- **Script GUIDs:** content asset files reference their script by the GUID in the script's `.meta`. Never delete
  or regenerate the `.cs.meta` of a ScriptableObject type. When creating a new SO type, let Unity generate its
  `.meta`, create assets through the Inspector (*Create → Astro Idle → …*), and commit both.
- Renaming a serialized field breaks existing assets. Use `[FormerlySerializedAs("oldName")]` if you must rename.

## 9. Events

- All global events live in `GameEvents`, raised only through its `Raise…` methods.
- Payloads: primitives, content definitions, or `readonly struct …Info` types in `AstroIdle.Events`.
- Subscribe in `Initialize`/constructor/`Create`. **Unsubscribe in `OnDestroy`/`Dispose`.** Missing unsubscribes
  cause leaks and duplicate handling after a progress reset reloads the scene.
- Handlers must not depend on the order other handlers run in. If order matters, use a direct call or polling.
- Don't raise events every frame. Use them for discrete occurrences.

## 10. Persistence

- Only `SaveService` touches the save file. Only services mutate `SaveData`, and only the fields they own
  (wallet → credits, upgrades → levels, and so on).
- Adding a field: give it a safe default. Older saves load it as that default.
- Changing or removing a field: bump `SaveData.CurrentVersion` and add a step in `SaveService.Migrate()`.
- Never store references to content assets in the save. Store ids.

## 11. Performance

- No allocations in per-frame paths: no LINQ, no `new List`, no string building in `Update` (UI text refresh is
  throttled to 5–10 Hz). Reuse buffers (`Projectile.SplashBuffer`).
- Avoid `GetComponent` in `Update`. Cache it in `Awake`/`Initialize`.
- Spatial queries go through `CombatRegistry`. Optimize there (spatial grid) if entity counts grow.
- Target 60 FPS on mid-range Android. Profile with **Window → Analysis → Profiler** on a device build before
  optimizing.

## 12. Testing

- Edit-mode tests live in `Assets/_Project/Tests/EditMode/`. Name files `<ClassUnderTest>Tests.cs` and methods
  `Method_Condition_Expectation` or a clear sentence.
- **Every pure formula or rule gets tests** (math classes, formatters, pickers, save data).
- `ContentValidationTests` must pass. It fails the build if shipped content is broken.
- Gameplay feel is verified by playtesting in the editor or on a device. Note the results in the PR or commit
  message.

## 13. Documentation

- **Every code folder has a `README.md`** covering: purpose, what each file/class does, how it interacts with
  other folders (with relative links), and step-by-step "how to" instructions for common changes.
- Parent READMEs link to child READMEs whenever they mention something inside them.
- **Docs change in the same commit as the code they describe.** A PR that changes behaviour without updating the
  relevant README or `docs/GAME_DESIGN.md` is incomplete.
- `docs/GAME_DESIGN.md` holds the authoritative balance tables and formulas.
- Keep docs factual and current. Delete outdated statements rather than leaving them.

## 14. Git

- Commit Unity `.meta` files with their assets/folders. Never commit `Library/`, `Temp/`, `Logs/`, `UserSettings/`
  or builds (see `.gitignore`).
- Small, focused commits with imperative subject lines: `Add chain lightning weapon`, `Tune wave HP growth to 1.14`.
- Branch per feature (`feature/prestige`, `balance/wave-curve`). Merge to `main` via PR when collaborating.
- If binary assets (art/audio) become large, set up Git LFS before adding them.

## 15. Checklists

### Adding content (weapon / enemy / milestone / upgrade)
- [ ] Follow the [content guide](../Assets/_Project/Resources/Content/README.md).
- [ ] Unique lower_snake_case id. Asset named `Type_Name.asset` in the correct folder.
- [ ] **Astro Idle → Validate Content** passes. Edit-mode tests pass.
- [ ] Tables in `docs/GAME_DESIGN.md` updated.

### Adding a system or class
- [ ] Placed in the correct layer folder and namespace. No upward dependencies.
- [ ] Dependencies injected. Events unsubscribed. No `Find*`.
- [ ] Pure logic extracted and unit tested.
- [ ] Folder README updated (and `docs/ARCHITECTURE.md` if the architecture changed).

### Changing a serialized type (Definition, Config, SaveData)
- [ ] Enums only appended. No field renames without `[FormerlySerializedAs]`.
- [ ] Existing `.asset` files still load the right values (check them in the Inspector).
- [ ] Save version and migration updated if `SaveData` changed shape.
